# sonar-fix

เป้าหมาย: issue ในขอบเขตหายจากการสแกนรอบหน้า โดยระบบทำงานเหมือนเดิมทุกกรณี — **พฤติกรรมเท่าเดิม** ต้องพิสูจน์ได้ ไม่ใช่เชื่อ

## Argument

| ส่วน | ตัวอย่าง | ไม่ใส่ |
|---|---|---|
| project key | `payroll-line-oa` | เลือกตามขั้น 1 ของ `.claude/skills/sonar-report/SKILL.md` |
| ขอบเขต (ใส่ได้หลายตัว) | `feature:leave`, `src/components`, `src/lib/getLeaveDetail.ts`, `rule:S3358` | ดึง issue ทั้ง project แล้วนับตามกลุ่ม (`src/features/<ชื่อ>` → `feature:<ชื่อ>`, นอกนั้น 2 ระดับแรกของ path) แสดงเป็นตาราง แล้วถามว่าจะแก้กลุ่มไหน |
| ยกเว้น | `ยกเว้น feature:attendance,payroll Dockerfile` | ไม่ยกเว้น |
| โหมด | `รวดเดียว` / `ทีละเฟส` | ถามตอนอนุมัติแผน (ขั้น 4) |

## กฎ

- issue หายเพราะโค้ดถูกแก้เท่านั้น: ไม่ใช้ `// NOSONAR`, `eslint-disable` และไม่เรียก `change_sonar_issue_status` / `change_security_hotspot_status`
- แก้เฉพาะไฟล์ในขอบเขต โค้ดของ feature ที่พักไว้หรือ edit mode ให้คงไว้ ถ้า issue แก้ได้ทางเดียวคือลบโค้ดพวกนี้ → จัดเป็น "รอตัดสินใจ"
- lookup ที่ key มาจาก backend, ชื่อไฟล์ หรือ input ภายนอก → ใช้ `Map` (object literal ตอบ key อย่าง `constructor`, `toString` จาก prototype ทำให้ผลต่างจากโค้ดเดิม)
- แยกฟังก์ชันหรือแยกตัวแปรออกจาก condition แล้ว ให้เช็กว่า TS narrowing ยังทำงานที่จุดใช้งานเดิม ถ้าหาย ให้คงเงื่อนไขนั้นไว้ inline
- ดึง type จาก mock handler หรือไฟล์อื่น → ตรวจว่ามาจาก handler/endpoint ตัวที่ถูกต้อง
- ไม่แก้ README ไม่ commit เอง ถ้าผู้ใช้สั่ง commit ห้ามมี `Co-Authored-By`

## จุดหยุด

ทั้งสองโหมดหยุดเสมอที่: อนุมัติแผน (ขั้น 4), issue ที่แก้แล้วพฤติกรรมเปลี่ยน, ก่อนทำสิ่งที่ย้อนกลับยาก (ลบไฟล์, git ที่เขียนประวัติ, แตะนอก repo)
- **รวดเดียว**: นอกจากจุดข้างบน ทำต่อจนจบ สถานะความคืบหน้าเขียนรวมในข้อความเดียวกับงานถัดไป
- **ทีละเฟส**: จบแต่ละเฟส สรุปสั้น (แก้อะไร, ผล typecheck/เทสต์) แล้วรอ "ไปต่อ"
ผู้ใช้เปลี่ยนโหมดกลางทางได้ ให้ทำตามโหมดล่าสุด

## ขั้นตอน

### 1. ดึง issue ในขอบเขต

tool ของ sonarqube เป็น deferred: โหลดด้วย `ToolSearch` ก่อนเรียก

ดึงจาก server ใหม่ทุกครั้ง แม้แชตนี้เคยแสดงรายงานหรือรายการ issue แล้ว — server อาจถูกสแกนใหม่ ทำให้ issue ที่แก้ไปแล้วยังอยู่ในแผน หรือเลขบรรทัดชี้ผิดที่

`search_sonar_issues_in_projects` ด้วย `issueStatuses: ["OPEN","CONFIRMED"]`, `ps: 500` และแบ่งหน้าจนครบ `paging.total`:
- โฟลเดอร์/ไฟล์ → `files: ["<key>:<path>"]` (`feature:leave` = `<key>:src/features/leave`) **ห้ามใส่ `projects` คู่กับ `files`** (server ตอบ 400)
- `rule:` หรือไม่มีขอบเขตแบบ path → `projects: [key]` แล้วกรองเองตาม `rule`
- ตัด issue ที่ตรง "ยกเว้น" ออก

เสร็จเมื่อ: ได้ issue ครบตาม `paging.total` ของทุกคำค้น และกรองยกเว้นแล้ว

### 2. เช็กกับโค้ดปัจจุบัน

ผลบน server อาจเก่ากว่าโค้ด เปิดทุกไฟล์ที่บรรทัดของแต่ละ issue แล้วจัดเป็น:
- **ต้องแก้**: โค้ดตรงนั้นยังผิด rule
- **แก้แล้ว รอสแกน**: โค้ดเปลี่ยนไปแล้วและไม่ผิด rule แล้ว
- **หาไม่เจอ**: ไฟล์ถูกลบ/ย้าย

เสร็จเมื่อ: ทุก issue มีสถานะ 1 ใน 3 ข้างบน

### 3. บันทึก baseline

```bash
npm run typecheck
npm test
```

จดว่า error/เทสต์ไหน fail อยู่แล้วก่อนแก้ (ชื่อเทสต์, ไฟล์:บรรทัดของ tsc error) — ใช้เทียบตอนปิดงาน

### 4. แผน + checklist แล้วหยุดรอ

สร้าง `sonar/fix-<YYYY-MM-DD-HHmm>-<key>.md` (`date +%Y-%m-%d-%H%M`) เป็น checklist ทีละ issue แบ่งเฟสตามกลุ่มหรือไฟล์:

```markdown
# sonar-fix: <key> · <ขอบเขต> · ยกเว้น <...>
โหมด: <รวดเดียว|ทีละเฟส>
Baseline: typecheck <n error> · test <n fail: ชื่อ>

## เฟส 1: <ชื่อ>
- [ ] `path:line` S3358 — <สาเหตุ> → <วิธีแก้> · ความเสี่ยง: <type only | logic: วิธีพิสูจน์>
...
## แก้แล้ว รอสแกน
## หาไม่เจอ
## รอตัดสินใจ
- `path:line` Sxxxx — <ทำไมแก้แล้วพฤติกรรมเปลี่ยน> → ก. <...> ข. <...>
```

rule ที่ไม่แน่ใจวิธีแก้ → `show_rule` ก่อนเขียนแผน

แสดงแผนในแชต (ตารางสรุปต่อเฟส + รายการรอตัดสินใจ) แล้วถามด้วย `AskUserQuestion` (ข้ามข้อนี้ถ้าใส่โหมดมาใน argument แต่ยังต้องรอ "ลงมือ"):
1. ลงมือ, ทำรวดเดียวจนจบ
2. ลงมือ, หยุดให้ดูทุกเฟส
3. แก้แผนก่อน

เสร็จเมื่อ: ทุก issue "ต้องแก้" อยู่ในเฟสใดเฟสหนึ่งหรือใน "รอตัดสินใจ" และผู้ใช้อนุมัติแล้ว

### 5. แก้ทีละเฟส

แต่ละ issue:
- **type only** (`Readonly<>`, `readonly`, type alias): แก้ แล้วพึ่ง typecheck
- **logic** (แยกฟังก์ชัน, แตก ternary, เปลี่ยน lookup, เปลี่ยน API ที่ใช้): ก่อนแก้ เขียนเทสต์ที่ล็อกผลของโค้ดเดิมให้ครอบทุก branch (truth table ของทุก input ที่ทำให้ผลต่างกัน รวม `undefined`/ค่าว่าง/key แปลก) รันให้ผ่านกับโค้ดเดิม แล้วจึงแก้ และรันให้ผ่านอีกครั้ง
- tick ใน checklist ทันทีที่ issue นั้นเสร็จ เจออะไรใหม่ให้เพิ่มลง checklist

ถ้า context ถูกสรุประหว่างทาง: อ่าน checklist แล้วทำต่อจากรายการแรกที่ยังไม่ tick

เสร็จเมื่อ (ต่อเฟส): ทุกรายการในเฟสถูก tick หรือย้ายไป "รอตัดสินใจ" พร้อมเหตุผล และ `npm run typecheck` ไม่มี error ใหม่เทียบ baseline

### 6. ตรวจ

1. `npm run typecheck`, `npm test`, `npx eslint <ไฟล์ที่แก้>` — เทียบ baseline: ต้องไม่มี error/fail ใหม่
2. review `git diff` ของตัวเอง หาเฉพาะปัญหาที่ควรกันไม่ให้ merge: พฤติกรรมเปลี่ยน, narrowing หาย, prototype key, แตะนอกขอบเขต — เจอให้แก้แล้ววนข้อ 1

เสร็จเมื่อ: ไม่มี error/fail ใหม่ และ review ไม่เจอปัญหาค้าง

### 7. สรุป

เรียงหัวข้อตามนี้:
1. **รอคุณตัดสินใจ** — จาก "รอตัดสินใจ" พร้อมตัวเลือก
2. **แก้แล้ว** — ต่อเฟส: จำนวน issue, ไฟล์, เทสต์ที่เพิ่ม
3. **เจอเพิ่ม** — สิ่งที่พบระหว่างทาง, "แก้แล้ว รอสแกน", "หาไม่เจอ"
4. **ยืนยันไม่ได้** — สิ่งที่พิสูจน์ไม่ได้ และดูจากไหนแล้ว (ไม่มีให้ตัดหัวข้อนี้)

ปิดด้วย: path ของ checklist และบอกให้สแกนใหม่เพื่อยืนยันว่า issue หาย
